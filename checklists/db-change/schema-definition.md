# 表结构定义子清单

适用范围：新建表、字段、索引、约束、字符集和字段类型变更。

## 命名与规范

- [ ] 表、字段、索引、约束和外键命名符合项目规范（如 user_account 表、created_at 字段）。
- [ ] 表名、字段名避免与数据库关键字冲突；必要时使用反引号或方括号保护。
- [ ] 枚举字段、状态字段、标志字段命名清晰（如 user_status、is_deleted）。

## 主键与约束

- [ ] 主键设计合理（自增、UUID、序列或分布式 ID），满足唯一性和排序性要求。
- [ ] 唯一约束准确表达业务规则（如 email 唯一但允许 NULL），多列唯一约束顺序合理。
- [ ] 非空约束只应用于必填字段；默认值表达真实业务规则。
- [ ] 外键约束是否有必要，on delete/update 策略（CASCADE、RESTRICT、SET NULL）是否满足需求。

## 字段类型与长度

- [ ] 字段类型选择符合业务需求：整数范围、精度、金额使用 decimal、JSON 使用 JSON 类型。
- [ ] 字符串长度满足实际需求（手机号 11、邮箱 255、名称 100）；避免过长导致索引低效。
- [ ] 时间字段类型明确（datetime、timestamp、date）和时区处理一致。
- [ ] 布尔字段使用 tinyint(1) 或 boolean，避免使用字符串。

## 字符集与排序

- [ ] 整库字符集统一（UTF-8 或 UTF-8MB4），避免字段级差异导致数据问题。
- [ ] 排序规则一致；不区分大小写的字段显式指定 COLLATE。
- [ ] 跨库迁移时字符集和排序规则兼容性已评估。

## 字段注释与文档

- [ ] 新增或调整字段有字段注释说明业务含义、范围、约束和单位。
- [ ] 新建表的全部字段有字段注释；不能为空或只写重复字段名。
- [ ] 枚举值、状态值的含义文档化（如 status: 0=待审批, 1=已通过）。
- [ ] 表注释说明业务用途和生命周期（如临时表、历史表）。

## 兼容性与版本

- [ ] 新增字段不会破坏现有应用的读写；旧应用能正确处理新字段。
- [ ] 字段删除、重命名、类型调整需遵循兼容顺序：新增字段 → 应用升级 → 删除旧字段。
- [ ] 默认值变更不影响已有数据和应用逻辑。
- [ ] 已有数据、旧版本程序、查询代码是否需要适配或迁移。

## 索引与性能考虑

- [ ] 主键索引自动创建；唯一约束自动创建唯一索引。
- [ ] 外键自动创建索引；避免重复创建相同的索引。
- [ ] 高频查询字段是否需要索引（WHERE、ORDER BY、JOIN 条件）。
- [ ] 索引顺序与查询条件匹配（如 WHERE a=? AND b=?, 索引为 (a, b)）。

## 常见陷阱

- [ ] 避免在同一表中创建过多索引（通常不超过 5-6 个），增加写入成本。
- [ ] 避免对低选择性字段单独创建索引（如性别字段）。
- [ ] 避免对经常修改的字段创建过多索引。
- [ ] JSON 字段查询是否使用生成列（MySQL 5.7+）或虚拟索引优化。

## 变更脚本与验证

- [ ] 变更脚本包含 DROP/TRUNCATE 前的备份和恢复计划。
- [ ] 变更脚本支持重复执行或回滚（使用 IF EXISTS、IF NOT EXISTS）。
- [ ] 大表变更（新增字段、修改类型）评估锁时间和在线 DDL 策略（MySQL 8.0+）。
- [ ] 变更前后的数据验证：字段计数、数据范围、样本数据抽查。

## 回滚计划

- [ ] 字段删除是否可逆（备份恢复或新增同名字段）。
- [ ] 类型收窄（如 int 改为 tinyint）是否可能丢失数据；回滚是否能恢复。
- [ ] 非空约束添加到有 NULL 值的字段需预处理；回滚需恢复 NULL。
- [ ] 外键约束添加需验证现有数据一致性；回滚时检查是否保留数据。
