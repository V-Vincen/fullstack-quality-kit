# 外部 API 文档整理清单

## 快速索引

- 适用范围：扫描和整理项目中的外部接口文档。
- 触发条件：用户明确要求扫描项目中的外部接口。
- 默认行为：只说“扫描”时，只读扫描并输出扫描结果。
- 文档行为：明确要求“整理”或“生成接口文档”时，才写入或修改接口文档。
- 执行顺序：范围确认 → 证据收集 → 官方核验 → 文档生成 → 全量复核 → 交付。
- 核心验收：来源、字段层级、类型、必填、默认值、地址、示例、错误码、链接和章节编号。
- 相关项目规则：读取项目记忆和资料索引。

## 清单路径解析

CHECKLIST_ROOT 先解析为当前项目/.codex/checklists/；不存在时再解析为 ~/.codex/checklists/fullstack-quality-kit/。以下路由均相对于 CHECKLIST_ROOT。

## 领域子清单路由

根据文档整理阶段继续读取：

- 接口发现：`CHECKLIST_ROOT/external-api-doc/api-discovery.md`
- 请求与响应契约：`CHECKLIST_ROOT/external-api-doc/api-contract.md`
- 错误与重试：`CHECKLIST_ROOT/external-api-doc/api-error-retry.md`
- 接口安全：`CHECKLIST_ROOT/external-api-doc/api-security.md`
- 版本兼容：`CHECKLIST_ROOT/external-api-doc/api-version-compatibility.md`

总清单负责范围、证据、文档结构和最终验收，领域子清单负责对应文档内容；只读扫描不得写入文档。

## 触发规则

### 只读扫描

用户只说以下内容时，只扫描，不修改文件：

~~~text
扫描一下项目里的外部接口
~~~

输出发现的外部企业或平台、接口名称、请求地址、请求方式、请求格式、请求和响应模型、项目来源、数据质量、核验状态和未确认事项。

### 扫描并生成文档

用户明确要求“整理”或“生成接口文档”时，扫描后再写入或修改接口文档，例如：

~~~text
扫描一下项目里的外部接口，并整理成标准接口文档。
~~~

此时才执行按企业拆分文档、官方资料核验、字段整理、示例格式化、错误码补充、来源登记和全量复核。

### 不触发

- 普通代码开发。
- 单个接口调试。
- 项目内部接口、Service、DAO 或数据库分析。
- 不涉及外部接口扫描的配置修改。

适用于扫描项目源码、官方文档和历史资料，整理外部企业 API¹ 接口文档的任务。

## 1. 执行前确认

- 明确本期目标、文档范围、输入目录、输出目录和交付格式。
- 只整理外部企业接口，不把项目内部同步、落库、定时任务、状态流转等业务逻辑写入接口正文。
- 确认企业分类方式：每个企业单独一个文档。
- 检查项目记忆、已有文档、官方资料归档和历史备份。
- 建立接口证据表后再开始生成正文。

## 2. 资料和证据规则

资料优先级固定为：

1. 官方接口页面、官方 API 文档和官方 SDK 文档。
2. 项目源码、配置、请求模型、响应模型和 SDK 调用。
3. 历史地址、本地说明、旧接口和源码注释。

字段类型、必填、默认值、描述、错误码和请求地址不一致时，以官方资料为准；项目差异只能作为来源说明，不能覆盖官方定义。

每条关键结论记录以下信息：

| 信息 | 要求 |
|---|---|
| 来源 | 官方页面、官方文档、源码文件、配置或历史资料 |
| 质量 | A：官方；B：项目源码或模型；C：历史资料或推断线索 |
| 核验状态 | 已核验、部分核验、未核验 |
| 证据位置 | 相对路径、接口名称、方法名或官方页面地址 |

没有证据不得臆造。只有项目代码而没有官方定义时，必须明确标注“项目来源，官方未核验”；没有实际接口内容时，不建立接口章节。

## 3. 文档结构

每个企业单独建立文档，统一使用以下结构：

~~~text
一、文档信息
二、环境、平台与鉴权
三、接口定义
  3.1 公共参数
  3.2 公共请求参数
  3.3 公共响应参数
  3.4 下单接口
  3.5 取消下单接口
  3.6 轨迹查询接口
  3.7 其他接口
  3.8 旧接口
术语注解
~~~

- 接口顺序固定为：下单、取消下单、轨迹查询、其他接口、旧接口。
- 没有实际内容的章节整体删除，不保留“暂无”“待确认”、空表格或空示例。
- 删除接口后必须重新检查章节编号、术语注解、目录和交叉引用。

## 4. 接口完整性

每个实际接口必须检查以下内容：

- 接口描述。
- 完整请求地址。
- 生产、测试、沙箱或旧环境标签。
- 请求方式。
- 请求格式、请求头和字符编码。
- 请求参数。
- 请求示例。
- 响应参数。
- 返回示例。
- 官方平台结果代码和业务错误码。

地址必须完整展示，不使用 `<HOST>`、变量名或无法解析的占位符。能使用域名时优先使用域名；没有可用域名时才保留 IP，并注明核验结果。不同地址独立成行。

## 5. 字段和层级规则

字段表固定使用以下列：

~~~text
参数 | 类型(约束) | 必填 | 默认值 | 描述
~~~

- 字段必须保留完整父子层级。
- 不能把 `waybillNoInfoList.waybillNo` 写成上级对象下的同级字段。
- 当前节点字段不超过两个时，可以在当前表格中展开。
- 当前节点字段超过两个时，必须拆分独立的“元素<请求>”或“元素<响应>”小节。
- 列表和列表对象必须继续展开，例如 `routeResps.routes`、`serviceList[].name`。
- 当前标题已经表达父节点时，表格不重复填写父节点；否则必须写完整路径。
- 类型以官方资料为准，统一使用 `String`、`Integer`、`Long`、`Boolean`、`List`、`List<T>`、`Object` 等写法。
- 不使用 `[]`、`Array[Object]` 等替代官方的 `List` 表达。
- 每个字段都必须核验类型、约束、必填、默认值和描述；未知项明确标注来源和核验状态。

## 6. 示例规则

- JSON³ 和 XML⁴ 示例必须先解析，再格式化展示。
- 去除反斜杠转义和重复的字符串包裹。
- 使用带语言标识的代码块：`json` 或 `xml`。
- XML 必须保留节点层级并缩进，不展示为单行字符串。
- 不使用 `{}`、`[]` 或无字段示例作为占位内容。
- 示例必须与请求参数、响应参数和应用场景一致；不能为了填充版面而补造字段。

## 7. SDK、旧接口和项目封装

- SDK² 类名、方法名和请求对象只能作为项目调用证据。
- 应尽量反查 SDK 对应的官方接口名称、地址和参数。
- 只能确认 SDK 调用时，必须注明“项目 SDK 调用，官方字段未完整核验”。
- 官方已废弃或停止更新的接口放入“旧接口”，不得与当前接口混写。
- 不得根据类名、方法名或业务类名臆造官方接口。

## 8. 来源和链接

- 项目源码来源统一使用相对路径。
- 官方资料附官方网站地址。
- 来源链接尽量定位到具体文件、接口或官方页面。
- 不把本机绝对路径写入交付文档。
- 可下载的官方 API 文档应归档到项目 `api-docs` 目录，并在索引中登记。

## 9. 删除和同步

删除一个接口或资料来源时，同时检查：

- 接口标题和接口描述。
- 请求、响应和错误码表格。
- JSON/XML 示例。
- 章节编号。
- 术语注解及编号。
- 目录、来源索引和交叉引用。
- 官方资料归档说明。

术语注解只保留正文仍然使用或确实解释当前接口内容的术语；删除无对应正文的术语，并重新编号。

## 10. 最终验收

交付前对全部文档执行全量检查：

- 文档范围只包含外部接口。
- 企业分类完整且没有重复归档。
- 章节编号连续。
- 每个接口都有完整地址和请求方式。
- 没有空接口章节、空表格或空 JSON/XML 示例。
- JSON/XML 可以实际解析。
- 代码块成对闭合。
- Markdown 表格分隔线正确。
- 嵌套字段路径完整。
- 字段元数据齐全且来源清楚。
- 错误码没有未经证实的解释。
- 来源链接使用相对路径或官方地址。
- 没有混入项目业务逻辑或跨项目字段差异分析。
- 官方、项目、历史资料的质量等级和核验状态已标明。

## 11. 交付记录

交付时分别报告：

- 设计版（S）：结构和规则是否确定。
- 数据版（D）：来源、字段和核验是否完成。
- 最终版（F）：文档、示例和全量验证是否完成。
- 修改文件、备份位置、验证命令、验证结果和已知限制。

### 术语注解

**API**¹：外部平台提供的调用接口。
**SDK**²：供应商提供的软件开发工具包。
**JSON**³：常用的结构化数据交换格式。
**XML**⁴：通过节点层级组织数据的结构化报文格式。
