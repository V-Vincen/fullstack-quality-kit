# TDD 验证工作流

## 用途

验证 Skill、清单、路由和脚本修改后的可观察行为。先定义修改前不能满足的场景，再以实际命令和结果证明修改生效。

## 触发条件

- 修改 Skill。
- 修改清单。
- 修改路由。
- 修改安装、卸载或验证脚本。
- 修改与业务行为、接口结果或页面交互相关的规则。

## 执行步骤

1. 记录修改前的基线行为、命令和结果。
2. 定义至少一个修改前失败或无法满足的场景。
3. 在已授权范围内执行最小修改。
4. 验证正常场景。
5. 验证异常场景。
6. 验证边界场景。
7. 验证重复执行场景。
8. 对比修改前后的结果。
9. 记录未覆盖项和已知风险。

## 最低覆盖范围

- 正常输入。
- 空值或缺失参数。
- 非法输入。
- 重复执行。
- 工作流文件缺失。
- 多个专业子 Skill 组合。
- 验证脚本失败。
- 路由未命中或错误命中。

优先执行：

~~~bash
./scripts/validate.sh
~~~

如需验证失败路径，应在临时副本中构造缺失文件或错误引用；不得删除、覆盖或破坏用户工作区中的文件。

## 输出格式

~~~text
实际执行命令：
实际结果：
通过项：
失败项：
未覆盖项：
已知风险：
~~~

## 边界

- 验证只覆盖本次已授权修改及其必要依赖，不把局部通过描述为全项目通过。
- 命令启动成功不等于验证完成；必须检查退出状态、关键输出和预期行为。
- 外部测试框架或能力可作为增强，但本工作流不以它们为硬依赖。

## 完成条件和回退

完成验证后，返回 fullstack-review 主流程交付结果。若验证失败，先说明触发场景、证据、根因、影响、修复方向和风险，再决定是否在已授权范围内修复。
