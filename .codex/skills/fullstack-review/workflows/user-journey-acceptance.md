# 用户流程验收工作流

## 用途

从普通用户实际会进入的页面开始，验证核心任务是否能被理解、完成和恢复。本工作流补充功能测试，不以页面元素存在或自动化点击成功代替用户体验结论。

## 触发条件

- 用户明确要求用户流程、上线前、体验或浏览器验收。
- 本次审查或修改覆盖登录、注册、提交、下单、付款、权限申请或其他核心用户流程。
- 需要确认功能虽可用但入口、反馈或恢复方式是否易于理解。

## 不触发条件

- 只涉及后端、数据库、脚本或不可见的内部实现，且不改变用户可见流程。
- 只需要静态代码审查、接口契约审查或常规测试用例生成。
- 没有可访问的测试页面、测试环境或已授权测试账号时；此时标记为未验证，不用推测代替实际体验。

## 执行步骤

1. 确认目标用户、核心任务、正常入口、测试环境、测试账号和不允许产生的真实后果。仅在缺失信息会影响验收结论时进入 `preflight-grill.md`。
2. 从普通用户可见的正常入口完成任务，不能使用内部地址、源码、隐藏接口或开发者知识绕过步骤。
3. 覆盖正常完成、失败、返回、刷新、中断和恢复等实际相关场景；按目标用户设备覆盖桌面端、移动端或目标浏览器。
4. 在每个关键步骤确认用户是否知道要做什么、能否发现入口、能否理解操作结果，以及是否知道下一步。
5. 结合实际浏览器渲染和截图检查可见文字、控件、状态反馈、布局和触摸或键盘操作。浏览器不可用时，将视觉和操作结论标记为未验证。
6. 区分功能故障、体验障碍和视觉偏好；问题必须有复现路径、证据、用户影响、最小改进方向和验证办法。
7. 完成后返回主流程，根据实际范围读取 `frontend-review`、`test-generation` 和相关业务测试清单。

## 输出格式

~~~text
验收目标：
已验证范围：
未验证范围与原因：
测试环境、账号和设备：
通过项：
问题项：类型、复现路径、证据、用户影响、最小改进、验证办法
真实后果边界：
~~~

## 边界

- 只使用已授权的测试环境、账号和测试数据。
- 创建账号、真实付款、对外发送、发布、删除或修改真实业务数据前必须停止并等待额外授权。
- 不以源码、接口或自动化脚本可执行替代普通用户能否理解和完成任务的证据。
- 本工作流不直接修改产品；发现问题后按用户授权和主流程处理。

## 完成条件和回退

验收完成后，交付实际操作证据、通过项、问题项和未覆盖范围。页面、账号、浏览器或授权条件不足时，明确说明验证边界，并回退到静态审查、测试用例或待确认结论。
